# وثيقة تسليم — وحدة مزامنة بيانات الطلاب (Student Sync Agent)

**موجهة للوكيل البرمجي المكلَّف بتطوير نظام الكنترول الجديد.**

## 1. الهدف
سحب بيانات الطلاب من جزء "شؤون الطلاب" في البرنامج القائم (ملف SQLite أو Access محلي) إلى قاعدة بيانات نظام الكنترول الجديد (PostgreSQL)، بشكل آمن، بدون تعارض مع البرنامج الحي، وقابل لإعادة التشغيل بدون تكرار بيانات.

## 2. الحقائق المؤكدة عن المصدر (لا تُخمَّن، مؤكدة من صاحب النظام)
- نوع الملف: **SQLite أو Access** (يُحدَّد بالضبط عبر `SOURCE_DB_TYPE` في `.env`).
- طرق الوصول المسموح بها: **(1)** اتصال مباشر Read-only بقاعدة البيانات، **و(2)** استدعاء الـ API الموجودة بالفعل بالبرنامج.
- البرنامج المصدر يعمل محليًا على عدة أجهزة (Desktop app) — الملف قابل للقفل وقت الاستخدام المتزامن.

## 3. القرارات التصميمية الملزمة (لا تُغيَّر بدون سبب موثّق)
1. **لا قراءة مباشرة من الملف الحي أبدًا.** كل قراءة تمر عبر `copy-source.js` أولاً (نسخة مؤقتة في `SNAPSHOT_DIR`)، ثم تُحذف النسخة بعد الانتهاء.
2. **الاستيراد الكامل (Full Sync)** يُستخدم للتحميل الأول ولإعادة المزامنة الدورية (يوميًا مثلاً)، عبر القناة المباشرة (SQLite/Access).
3. **مزامنة الفروقات (Delta Sync)** تُستخدم للتحديثات اللحظية/المتكررة، عبر الـ API الموجودة — **وليس** عبر إعادة قراءة الملف كل مرة.
4. **مفتاح التطابق الوحيد** بين المصدر والهدف هو `national_id` (الرقم القومي). أي سجل بدون رقم قومي يُسجَّل في اللوج ويُتخطى، لا يُستورد.
5. الاستيراد **Upsert فقط** (`INSERT ... ON CONFLICT DO UPDATE`) — لا حذف تلقائي لأي طالب موجود بالفعل بنظام الكنترول حتى لو اختفى من المصدر (الحذف يتطلب مراجعة يدوية دائمًا).

## 4. مهام غير مكتملة يجب إنجازها قبل التشغيل الفعلي (Blocking Tasks)
هذه ليست اجتهادًا — لازم تُنفَّذ بالترتيب:

| # | المهمة | كيف |
|---|---|---|
| 1 | تحديد نوع الملف الفعلي (SQLite أو Access) بدقة | افتح الملف أو اسأل مطوّر البرنامج الأصلي |
| 2 | اكتشاف أسماء الجداول/الأعمدة الحقيقية | شغّل `npm run discover` وراجع المخرجات |
| 3 | تحديث كل أسطر TODO في `src/mapper.js` بالأسماء الحقيقية | تعديل مباشر للملف |
| 4 | تأكيد القيم الفعلية لحقول: النوع، حالة القيد، حالة الدمج، نوعية التعليم (نصوص عربية؟ أكواد رقمية؟) | من عينة بيانات حقيقية، ثم تحديث `normalizeGender` وأي دوال تطبيع مشابهة |
| 5 | فحص استجابة API حقيقية وتعديل `fetch-from-api.js` حسب شكلها الفعلي | استدعاء تجريبي + مطابقة الحقول |
| 6 | تنفيذ `schema.sql` على قاعدة بيانات الكنترول قبل أول تشغيل | `psql -f schema.sql` |
| 7 | لو المصدر Access: تأكيد أن سكريبت المزامنة سيعمل على جهاز Windows به Access Database Engine مثبت | بيئة التشغيل |

## 5. بنية المشروع
```
sync-agent/
  package.json
  .env.example          ← انسخه إلى .env واملأ القيم الحقيقية
  schema.sql             ← نفّذه على PostgreSQL قبل أول مزامنة
  src/
    config.js            ← تحميل الإعدادات من .env
    copy-source.js        ← نسخ آمن قبل القراءة (لا يُتجاوز أبدًا)
    discover-schema.js    ← يُشغَّل يدويًا أولاً لاكتشاف البنية الحقيقية
    read-sqlite.js         ← قراءة من SQLite
    read-access.js          ← قراءة من Access عبر ODBC (Windows فقط)
    fetch-from-api.js        ← جلب فروقات عبر الـ API الموجودة
    mapper.js                 ← تحويل الحقول (فيه كل TODOs المطلوب حسمها)
    upsert-postgres.js         ← إدراج/تحديث آمن بمفتاح الرقم القومي
    sync.js                     ← نقطة التشغيل الرئيسية (full/delta)
```

## 6. التشغيل
```bash
npm install
cp .env.example .env   # ثم املأ القيم الحقيقية
npm run discover       # خطوة إلزامية أولى — لا تخطاها
npm run sync:full      # الاستيراد الكامل الأول
npm run sync:delta     # لاحقًا: مزامنة الفروقات عبر الـ API
```

## 7. نقاط لم تُحسم بعد وتحتاج قرار من صاحب النظام (وليس افتراضًا من الوكيل)
- هل الملف الفعلي SQLite أم Access؟ (الاثنان مدعومان بالكود، لكن لازم تحديد واحد في `.env`)
- هل يوجد عمود تاريخ تعديل (`updated_at`) بالمصدر لدعم Delta Sync حقيقي بدل جلب كل شيء كل مرة؟
- ما هي دورية تشغيل `sync:full` المطلوبة (يوميًا؟ كل ساعة؟ عند الطلب فقط)؟ — يحدَّد لاحقًا عبر جدولة (cron / Windows Task Scheduler) خارج نطاق هذا الكود.
